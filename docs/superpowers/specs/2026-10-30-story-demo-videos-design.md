# Story demo videos

Status: draft for the owner's review. Decisions marked **(owner)** are the owner's; **(my call)** are mine and open to correction.

This builds on "Spaces and the run guide" (PR #26, merged): the run guide that starts any project's app, and the runner that drives the confined agent in it. It comes after "Where intents are stored" (`2026-10-30-intent-storage-design.md`), which moves intents to `~/.helmsmith/intents/spaces/<space>/`.

## Why

When an intent's work is done, the owner wants to show it to a stakeholder: someone who wasn't in the conversation and may not know the app's insides **(owner)**. Today the tool can only link skoolscout's hand-written app-demos stories (`- demo: <story-id> (criteria: 1, 4)` lines, Playwright YAML recorded with `make demos`). Those exist only for skoolscout, and only when someone wrote them.

The owner wants:
- **Demo creation independent of app-demos (owner).**
- **Usable on any project (owner).**
- **User stories generated by the intent,** each video showing that story's acceptance criteria **(owner)**.

## What it does

### 1. Stories are written during polish (owner)

- **Story names come early (owner: "a clean indication of story should be known").** While the polish conversation runs, the intent shows which stories it will have. The names arrive with the write-up and every later write-up, not with each question turn **(my call)**.
- **Drafts come once every open question has an answer (owner).** The stories depend on those answers. Until then each story shows its name and what it shows, marked "draft waits for N open questions" **(my call)**.
- **When the last question gets its answer later (my call),** in a later polish with `p` or by `Q`, the tool asks the polish agent for the drafts in one more turn. The drafts are shown for review, as the write-up is.
- **Which kinds get stories (my call):**
  - features always;
  - bugs get one story showing the fixed behaviour, beside the existing before and after captures;
  - refactors and ideas get none, since nothing visible changes or nothing is built yet.

### 2. What a story says (owner: persona, starting data, steps, criteria shown)

A `## Stories` section after `## Acceptance criteria`, one `###` per story **(my call)**:

```markdown
## Stories
### Mark reinstates Maya's withdrawn application
- persona: Mark, a tenant admin
- shows: 1, 3
- starting data: Maya has a submitted application, then withdrawn
1. Open Maya's application from Applications
2. Choose Reinstate and confirm
3. See the application back under Submitted
```

- **`shows:` names criteria by number,** counted from 1 across groups as demo lines and the completion check count them today **(my call)**. A reconcile or fold that renumbers criteria renumbers `shows:` too, matching each criterion by its wording, as it already does for demo lines.
- **Coverage:** the write-up names any criterion no story shows, for example a log-only criterion. That is allowed but listed **(my call)**.
- **Stories are plain markdown,** editable like any other section.
- **They go out with the intent (my call, following the owner's reasoning).** The send prompt already includes the intent's body, so the coding agent sees from the start what will be demonstrated.

### 3. Recording: after the completion check passes (owner)

When the completion check passes, the tool records each story **(owner: "after the completion check passes, to show the stakeholder")**.

- **What "passes" means (owner, agreeing to my recommendation):** no criterion is failing or missing, counting the results of every check so far.
  - Partial re-checks count. For example, a re-check of the one criterion a fix closed completes the set.
  - "Can't check" doesn't block. Those are usually log-only criteria that no story shows. A story that shows one simply keeps no video, because its caption never comes.
- **Recording again on its own (owner, agreeing to my recommendation):** a story that already has a kept video records again automatically only when a criterion it shows was re-checked since that video. A partial re-check therefore keeps the app up for the stories that need it.

- **Starts on its own (my call),** in the same app run the check started, right after it. The app does not start twice.
- **Re-recording by hand (my call):** a key on a story records it again, but only after the intent's check has passed.
- **A third runner job (my call),** beside capture and check, using part 1's run guide in both modes: skoolscout's `work` slots, or a generic space's `start` command.

**Before the take (owner: the agent sets up the starting data through the UI, before recording):**
1. The guide's own seed commands run, as in part 1. Commands still come only from the guide.
2. The agent signs in as the story's persona, using that persona's test account from the guide's Stories section (below). The intent never holds a password.
3. The agent creates the story's starting data by using the app. It may sign in as any other persona the guide lists to do that, for example a parent who submits Maya's application. It creates only what the guide allows. None of this is recorded.
4. The agent rehearses the steps once, all the way through, unrecorded, to find the real path **(my call)**.
5. The rehearsal used up the starting data (it reinstated Maya's application), so the agent sets up fresh starting data again before the take, with new records **(my call)**. The setup happens twice, and each story's time limit allows for that.

**The steps the rehearsal found are saved beside the video, not written into the intent (my call).** The take follows them. The intent's draft stays as written. Why:
- the agent writes this text from app pages, which may hold text users entered;
- the intent's body goes to coding agents, so text from pages never enters it, for the same reason captions use only the intent's own criterion text;
- a re-record starts again from the intent's draft.

**The take (owner: one video per story, showing its criteria):**
- **Recording starts at step 1,** after sign-in and setup. No password or sign-in code is ever on video **(my call)**.
- **Opening card:** the story's name and persona. **Closing card:** the criteria it showed **(my call)**.
- **A `caption` tool (my call).** The agent calls it with a criterion's number at the moment that criterion is visible. The tool shows that criterion's own text over the page, so the caption is in the recording.
  - The agent passes a number, never text.
  - The agent still cannot run page scripts: `eval` stays refused, and the tool draws the caption with its own fixed code.
- **Kept only if every criterion the story shows got its caption (my call),** as the check keeps only proven verdicts. Otherwise no video is kept, and the story reads "criterion 3 didn't show".
- **Pace (my call):** slow enough to follow, with visible mouse movement.

**Data left behind (my call: a known limit).** Setup through the UI leaves records in the app, so a story run twice meets its own leftovers. The agent is told to create fresh records, with new names, when leftovers get in the way. Resetting data stays the guide's seed's job.

### The run guide's Stories section: the guide's rules win (owner, agreeing to my recommendation)

The run guide (`run.md`, part 1) gets a short `## Stories` section in its instructions:
- **Personas:** who stories may use, each with a test account and how it signs in.
- **What setup may create:** for example applications and notes, but not new people.

Rules:
- **The guide decides what's allowed, not the story.** Where the guide's general rules forbid something, such as "never sign up a new person", the story can't do it.
- **The drafting turn in polish reads this list,** so stories use only listed personas. If no listed persona fits, the draft says so instead of inventing one.
- **No Stories section:** stories are still drafted, with personas left as "unknown", and recording stops with "the run guide lists no personas for stories" **(my call)**.
- **Skoolscout's guide** needs a parent account added to its list for stories like the example. That's a change to skoolscout-com's guide branch, made on the owner's word.

### 4. Where videos live and how they're shared (owner: no S3; the developer copies the video and shares it)

- **Stored locally, with the intent (owner).** With profile storage (see `2026-10-30-intent-storage-design.md`), that is under `~/.helmsmith/intents/spaces/<space>/`, outside any repo.
  - Each story gets a folder at `<stem>.assets/stories/<n>-<slug>/` holding the video, the steps the take followed, and the run's log **(my call)**.
  - When meta storage is built later, videos stay out of git **(owner: "videos can be git ignored")**.
- **The card's Stories section** lists each story with its state: video, recording, "criterion N didn't show", or not recorded yet **(my call)**.
- **Keys on a story line (my call):**
  - `o` plays the video;
  - a key copies the video. On a Mac it copies the file itself, which pastes into Slack or Messages as an attachment; elsewhere it copies the file's path;
  - a key shows it in Finder or the file manager.

### 5. App-demos stays as it is (my call)

Skoolscout's `- demo:` lines and the app-demos reader keep working unchanged. Intent stories are separate: no Playwright, no app-demos files.

## Goals

- Polishing a feature ends with draft stories that cover its criteria, before the intent is sent.
- Once the check passes, each story has a captioned video on the developer's machine, on any project with a run guide.
- A developer hands a stakeholder a story's video with two key presses.

## Non-goals

- Uploading or hosting videos: no S3 **(owner)**.
- Turning intent stories into app-demos or Playwright stories.
- One joined video of all stories **(my call: later, keeps it simple)**.
- Voice-over or video editing.
- Recording before the check passes.

## Anti-goals

- A password, code or sign-in screen on video.
- A video that suggests a criterion works when the take didn't show it.
- Captions in the agent's own words. Captions are the intent's criterion text.
- Commands from the intent, a story or the agent. Guide commands only, as in part 1.

## Constraints

- The confined agent stays confined: browser-only tools, now plus `caption` and recording, under `--restricted --permission-mode dontAsk --tools ""`.
- Part 1's runner, lock, time limits and clean-up apply to story runs too.
- Tests start no real app, browser or agent. They use the existing fakes (`fake-gh.sh`, the fake provider and the fake agent-browser) and a fake `start`.
- No push, merge or release without the owner's word.

## Left to the builder

- The exact key letters, caption and card look, pacing, and per-story time limit.
- How the persona finds its test account in the guide's instructions.
- Video format: what agent-browser records (`.webm`), with or without `ffmpeg`. Cards and captions should not need `ffmpeg` if that can be avoided.
- How the drafts turn arrives in the polish conversation, and its review screen.
